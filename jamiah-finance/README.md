# হিসাব ও অর্থ বিভাগ — ভিত্তি মডিউল

Jamiah Scholars International · Node.js + Express + MySQL 8

ফান্ড-ভিত্তিক ডাবল-এন্ট্রি হিসাব ব্যবস্থা। যাকাত, সদকা, এতিম ও ওয়াকফ ফান্ড
আলাদা রেখে শরীয়তসম্মত ব্যয় নিয়ন্ত্রণ করে।

## Express-এ যুক্ত করা

```js
const mysql = require('mysql2/promise');
const VoucherService = require('./voucher-service');

const pool = mysql.createPool({
  host, user, password, database,
  decimalNumbers: true,   // টাকার হিসাব ঠিক রাখে
  dateStrings: true,      // তারিখ টাইমজোনে একদিন পিছিয়ে যায় না
});
const vouchers = new VoucherService(pool);

app.post('/admin/ledger/vouchers', requireAuth, async (req, res) => {
  try {
    const result = await vouchers.create(req.body, {
      userId: req.user.id, role: req.user.finance_role, ip: req.ip,
    });
    res.json({ ok: true, ...result });
  } catch (e) {
    if (e.name === 'VoucherError') return res.status(422).json({ ok: false, errors: e.errors });
    throw e;
  }
});
```

`e.errors` বাংলা বার্তার অ্যারে — সরাসরি ফর্মের পাশে দেখানোর উপযোগী।

অন্য মডিউল (ফি ইনভয়েস, বেতন, অনুদান, রশিদ) কখনো সরাসরি ব্যালেন্স আপডেট করবে না —
সবাই `vouchers.create()` ডাকবে, `source_module` ও `source_ref_id` দিয়ে।
সব হিসাব এক দরজা দিয়ে ঢুকলে খতিয়ান কখনো বেহিসাব হবে না।

### এন্ট্রি ফর্মে যা করা হয়েছে

- **নগদের লাইন হাতে লিখতে হয় না।** খরচ/জমা ভাউচারে শুধু ব্যয়/আয়ের লাইন আর
  `পরিশোধ হবে কোথা থেকে` বাছুন — বিপরীত লাইন নিজে বসে যায়।
- **একাধিক ফান্ডে ভাগ হলে নগদের দিকও ভাগ হয়।** Tk ৬০,০০০ এর বাজারে ৪৫,০০০ যাকাত
  ফান্ড আর ১৫,০০০ সাধারণ ফান্ড হলে নগদের ক্রেডিটও দুটো লাইনে ভাগ হয়ে যায়।
  এতে `v_fund_cash_split` সঠিক থাকে — কোন ফান্ডের টাকা কোথায় আছে, তা মেলে।
- **জার্নাল মোড:** JV/CV/FT-তে ডেবিট ও ক্রেডিট দুটো কলামই খোলা, অটো লাইন নেই।
- **হিসাব খোঁজা:** কোড বা বাংলা নাম — `5201` বা `খাবার` দুটোতেই আসে। তীর চিহ্ন + Enter।
- **কীবোর্ড:** Enter — নতুন লাইন · Ctrl+Enter — সংরক্ষণ। ফান্ড আগের লাইন থেকে ধরে রাখে।
- **লাইভ:** মোট, সমান কি না, আর প্রতিটি ফান্ডের জের `আগে → পরে`।
- **অনুমোদন স্তর আগেই জানায়:** `সরাসরি পোস্ট হবে` নাকি `মুহতামিমের অনুমোদনে যাবে`।
- **নিষিদ্ধ খাত লাইনেই লাল হয়;** মুহতামিম/কমিটি হলে ফতোয়া নোটের বাক্স খোলে।
- **প্রিন্ট:** ভাউচারের বিস্তারিত ও দিনের খতিয়ানে স্বাক্ষরের ঘরসহ প্রিন্ট স্টাইল।

### একটি সচেতন সিদ্ধান্ত

ফর্মের ফান্ড জের **পেজ লোডের সময়ের স্ন্যাপশট**। তাই ফান্ডে টাকা না থাকলেও
সংরক্ষণ বোতাম বন্ধ করা হয় না — শুধু ⚠ সতর্কতা দেখানো হয়, আর সার্ভার সংরক্ষণের
সময় আবার যাচাই করে আটকায়। নইলে পাশের টেবিলে কেউ টাকা জমা দিলেই বাসি জের দেখে
বৈধ ভাউচার আটকে যেত। বোতাম বন্ধ হয় শুধু অপরিবর্তনীয় বিধিনিষেধে — ওয়াকফ কর্পাস।

### যা যোগ করতে হবে

- **CSRF টোকেন** — আপনার প্যানেলে এখন csrf মেটা ট্যাগ নেই। POST রিকোয়েস্টে টোকেন
  যোগ করলে `voucher-entry.js` / `voucher-actions.js` এর fetch হেডারে বসাতে হবে।
- **পক্ষ (party) নির্বাচন** — এখন আইডি হাতে লিখতে হয়; শিক্ষার্থী/স্টাফ/দাতার
  সার্চ-পিকার বসালে দ্রুত হবে।
- **সংযুক্তি আপলোড** — টেবিল ও API প্রস্তুত, আপলোড হ্যান্ডলার বাকি।
- **রিকারিং/টেমপ্লেট ভাউচার** ও **অফলাইন এন্ট্রি** — পরের ধাপ।

## রোল

`accountant` → `chief_accountant` → `principal` → `committee`

অনুমোদনের স্তর ঠিক হয় দুটোর মধ্যে যেটা বড় তা দিয়ে: টাকার পরিমাণের স্তর,
আর ফান্ডের নিজস্ব `requires_approval_by`। ফলে ওয়াকফ ফান্ডে Tk ১০০ হলেও কমিটি লাগে।

স্তর বদলাতে:

```js
new VoucherService(pool, {
  approvalTiers: [
    { maxAmount: 5000,     role: 'accountant' },
    { maxAmount: 50000,    role: 'chief_accountant' },
    { maxAmount: Infinity, role: 'principal' },
  ],
});
```

## যাকাত নিয়ন্ত্রণ

`fund_account_rules` এ `allow` সারি থাকলে ফান্ডটি হোয়াইটলিস্ট মোডে চলে — তালিকার
বাইরে কোনো ব্যয় হবে না। যাকাতের জন্য অনুমোদিত: খাবার, চিকিৎসা, পোশাক, কিতাব,
এতিম বিশেষ ব্যয়, ফি মাফ (৫২০১–৫২০৬)। বিদ্যুৎ, বেতন, নির্মাণ, অফিস খরচ ব্লকড।

প্রতিষ্ঠানভেদে তামলিক/হীলার সিদ্ধান্ত ভিন্ন হয়, তাই `fatwa_override: true` +
`fatwa_note` দিয়ে মুহতামিম লিখিত কারণে অতিক্রম করতে পারেন — অডিট লগে স্থায়ী থাকে।
**ওয়াকফ কর্পাস এর ব্যতিক্রম — override দিয়েও ভাঙা যায় না।**

### তিনটি নকশাগত সিদ্ধান্ত

**১. রশিদ আর ভাউচার একই লেনদেনে।** `receipt-service.js` নিজের লেনদেন খুলে
`VoucherService.create(..., { conn })` ডাকে, তাই দুটোই হয় বা কোনোটাই হয় না।
রশিদের নম্বরও সেই লেনদেনের ভেতরে বাড়ে — ভাউচার যাচাইয়ে আটকালে নম্বরটা ফেরত
যায়, সিরিজে ফাঁক পড়ে না। (পরীক্ষায় এটা আলাদাভাবে যাচাই করা হয়েছে।)

**২. রশিদের ভাউচার সাথে সাথেই পোস্ট হয়।** টাকা হাতে এসে গেছে; অনুমোদনের
অপেক্ষায় ঝুলিয়ে রাখলে খতিয়ান পিছিয়ে থাকত আর কারণিক বুঝতে পারত না টাকাটা
হিসাবে ঢুকেছে কি না। এর জন্য `VoucherService` এ `opts.autoPost` যোগ করা হয়েছে —
অনুমোদনের স্তর এড়ানো হয়, কিন্তু **সব ভ্যালিডেশন চলে**। জমায় কোনো ফান্ড ঋণাত্মক
হওয়ার সুযোগ নেই, তাই এটা নিরাপদ।

**৩. শিক্ষার্থী ফির রশিদে ফান্ডের জের বদলায় না** — বদলায় শুধু নগদ আর বাকি ফি।
আয় আগেই ধরা হয়েছে মাসিক ইনভয়েসে (১২০১ ডেবিট / ৪১০২ ক্রেডিট)। এটাই সঠিক
accrual হিসাব। তাই ফি রশিদ কাটার আগে ওই মাসের ইনভয়েস তৈরি থাকা দরকার, নইলে
বাকি ফি হিসাবের জের ঋণাত্মক দেখাবে।

### রশিদে যা থাকে

প্রতিষ্ঠানের নাম, রশিদ নম্বর, বাংলা তারিখ, দাতার নাম ও মোবাইল, খাত, ফান্ড,
মাধ্যম (চেক/TrxID সহ), **অঙ্কে ও কথায় পরিমাণ**, স্বাক্ষরের ঘর, আর **QR কোড**।

- **তিন মাপে প্রিন্ট:** `?size=a4` · `?size=half` · `?size=thermal` (৭৬mm)
- **নকল কপি:** প্রথম প্রিন্টের পর প্রতিটি কপিতে তির্যক "নকল কপি" জলছাপ বসে
  (`print_count` গোনা হয়)
- **বাতিল রশিদে** লাল "বাতিল" জলছাপ ও কারণ ছাপা হয়
- টাকা কথায় ইস্যুর সময়েই `amount_in_words` এ সংরক্ষিত — পরে লাইব্রেরি বদলালেও
  পুরনো রশিদ অপরিবর্তিত থাকে

### QR যাচাই

QR কোড `/verify/<৩২ অক্ষরের র‍্যান্ডম টোকেন>` এ নিয়ে যায়। পেজটি **লগইন ছাড়াই**
খোলে, কারণ দাতা স্ক্যান করবেন। টোকেন ক্রমিক নয় বলে অনুমান করে অন্যের রশিদ দেখা
যায় না, আর পেজে **মোবাইল নম্বর ও ঠিকানা ইচ্ছে করেই দেখানো হয় না** — শুধু রশিদ
নম্বর, তারিখ, ধরন, নাম, খাত ও পরিমাণ। বাতিল হলে পেজ সেটাও কারণসহ জানায়।
জাল রশিদ ঠেকাতে এটাই সবচেয়ে কাজের।

### ম্যানুয়াল রশিদ বই

মাঠ কলেক্টরদের ছাপানো বইয়ের রেজিস্টার: কোন বই (নম্বর ১০০১–১১০০) কার কাছে,
কতটা ব্যবহার হয়েছে, ফেরত এসেছে কি না। বইয়ের রশিদ অনলাইনে তোলার সময় সিস্টেম
যাচাই করে — বইটি কাউকে দেওয়া আছে কি না, নম্বরটি বইয়ের পরিসরের ভেতরে কি না,
আর আগে ব্যবহার হয়েছে কি না।

### যা এখনো বাকি

- **দাতা CRM** — এখন `payer_name` টেক্সট; দাতাদের আলাদা টেবিল হলে পুনরাবৃত্ত
  দাতা চেনা যাবে, বার্ষিক রিপোর্ট পাঠানো যাবে (স্পনসর বিভাগের কাজ)
- **SMS / WhatsApp** — রশিদের লিংক পাঠানো
- **অনলাইন পেমেন্ট গেটওয়ে** — বিকাশ/নগদ/SSLCommerz থেকে অটো রশিদ
- **অফলাইন এন্ট্রি** — ইন্টারনেট ছাড়া রশিদ কেটে পরে সিংক
- প্রতিষ্ঠানের নাম-ঠিকানা-লোগো এখন `views/receipt-views.js` এর `ORG` এ হার্ডকোড;
  `settings` টেবিলে নেওয়া উচিত (রাউটারে `org` অপশন দিয়ে এখনই বদলানো যায়)

### মোবাইল নম্বরই দাতা চেনার চাবি

রশিদ কাটার সময় মোবাইল নম্বর দিলে পুরনো দাতা খুঁজে পাওয়া যায়, নইলে নতুন রেকর্ড
তৈরি হয় — কারণিককে আলাদা করে "দাতা যোগ করুন" ধাপে যেতে হয় না। নম্বর এক চেহারায়
আনা হয়, তাই `01711223344`, `+8801711223344`, `8801711223344` আর `0171-122 3344`
একই দাতা। বিদেশি নম্বরও অঙ্কে নামিয়ে আনা হয়, নইলে `+971…` আর `971…` দুই দাতা
হয়ে যেত।

পুরনো দাতার **নাম বদলায় না** (প্রথমবারের বানানই থাকে), শুধু **খালি ঘরগুলো** ভরে —
পরে ঠিকানা বা জেলা পেলে যোগ হয়, কিন্তু আগের তথ্য মুছে যায় না।

`receipt_types.links_donor` ঠিক করে কোন ধরনে দাতা রেকর্ড হবে। শিক্ষার্থী ফি ও
ঋণ ফেরতে **হয় না** — নইলে অভিভাবকদের নামে CRM ভরে যেত আর নিষ্ক্রিয় দাতার
তালিকা অর্থহীন হয়ে পড়ত।

### ডুপ্লিকেট দাতা একীভূত করা

একই মানুষ দুই রেকর্ডে ঢুকে পড়া অনিবার্য (একবার নম্বর ছাড়া, একবার নম্বর দিয়ে)।
তালিকায় দুটি টিক দিয়ে একীভূত করা যায় — রশিদ, প্রতিশ্রুতি ও মাসিক পরিকল্পনা
রাখা রেকর্ডে চলে যায়। পুরনো রেকর্ড **মুছে ফেলা হয় না**, `merged_into_id` দিয়ে
চিহ্নিত হয়, তাই ইতিহাস থাকে আর পুরনো লিংকও কাজ করে। রাখা রেকর্ডে নম্বর না
থাকলে পুরনোটির নম্বর সেখানে চলে যায়, তাই ওই নম্বরে পরের দান ঠিক জায়গায় বসে।

> সীমাবদ্ধতা: দুটি রেকর্ডেই নম্বর থাকলে একটি নম্বর হারায় (মোবাইল অদ্বিতীয়)।
> হারানো নম্বরটি নোটে রাখা হয় না — দরকার হলে `donor_mobiles` নামে আলাদা টেবিল লাগবে।

### প্রচারাভিযান

লক্ষ্য, সংগৃহীত, দাতার সংখ্যা, অনাদায়ী প্রতিশ্রুতি আর দিন বাকি — সব
`v_campaign_progress` ভিউ থেকে, আলাদা হিসাব রাখা হয় না, তাই কখনো বেহিসাব হবে না।

রশিদ কাটার সময় প্রচারাভিযান বাছা যায়। **ক্যাম্পেইনের ফান্ডই চূড়ান্ত** — ধরনে ফান্ড
বদলের অনুমতি থাকলে সেটাই বসে, না থাকলে স্পষ্ট বার্তা দিয়ে আটকায় (যাকাতের টাকা
নির্মাণ প্রকল্পে যেতে পারে না)।

### প্রতিশ্রুতি (Pledge)

কেউ ৫০ হাজার বলেছেন, ২০ হাজার দিয়েছেন — বাকি ৩০ হাজারের ফলো-আপ এখান থেকেই।
রশিদ প্রতিশ্রুতির সাথে যুক্ত হলে অবস্থা নিজে বদলায়: `open → partial → fulfilled`,
আর **রশিদ বাতিল হলে আবার পিছিয়ে আসে**। পূর্ণ প্রতিশ্রুতিতে আবার টাকা নেওয়া যায়
না, অন্য দাতার প্রতিশ্রুতিতেও নয়।

ফলো-আপ তালিকা মেয়াদ পেরোনো আগে সাজায়, পছন্দের যোগাযোগের মাধ্যম দেখায়, আর
"রিমাইন্ড করা হলো" চাপলে গণনা ও তারিখ রাখে — একই দাতাকে বারবার ফোন করা এড়াতে।

### মাসিক নিয়মিত দাতা

`recurringDue(তারিখ)` বলে দেয় এ মাসে কার টাকা আসার কথা ছিল কিন্তু আসেনি —
মাসের তারিখ পেরিয়েছে, অথচ ওই মাসে ওই পরিকল্পনার বিপরীতে কোনো রশিদ নেই।
ফাংশনটি তারিখ প্যারামিটার নেয়, তাই "আজ" এর ওপর নির্ভর না করেই পরীক্ষা করা যায়।
তালিকা থেকে সোজা রশিদ কাটার লিংকে যাওয়া যায় (দাতা ও পরিকল্পনা আগেই বসানো থাকে)।

### নিষ্ক্রিয় দাতা — সবচেয়ে কাজের রিপোর্ট

আগে দিয়েছেন, কিন্তু ৬ মাস (বদলানো যায়) ধরে কিছু দিচ্ছেন না। নতুন দাতা খোঁজার
চেয়ে এঁদের ফিরিয়ে আনা অনেক সহজ। যাঁরা **যোগাযোগ করতে নিষেধ করেছেন**
(`allow_contact = 0`) তাঁরা এই তালিকায় ও ফলো-আপে আসেন না — এটা মানা দরকার।

### বার্ষিক বিবরণী

দাতাকে পাঠানোর জন্য প্রিন্টযোগ্য "আপনার টাকা কোথায় গেল": রশিদ ধরে ধরে তালিকা,
ফান্ড অনুযায়ী ভাগ, মোট অঙ্কে ও কথায়, কৃতজ্ঞতার বার্তা ও স্বাক্ষরের ঘর।
বাতিল রশিদ এতে আসে না।

### আরও রিপোর্ট

মাস-ওয়ারি সংগ্রহ গত বছরের একই মাসের পাশে (শতকরা পরিবর্তনসহ), টপ ১০ দাতা,
আর এলাকাভিত্তিক সংগ্রহ — প্রবাসী দাতা আলাদা করে। সবগুলোই সাধারণ CSS বার,
কোনো চার্ট লাইব্রেরি নেই।

### যা এখনো বাকি

- **SMS / হোয়াটসঅ্যাপ** — রিমাইন্ডার ও বিবরণী পাঠানো এখন ম্যানুয়াল
- **এতিম স্পনসর বিভাগ** — `sponsorship_id` ঘর ও `ORP` ফান্ড প্রস্তুত, কিন্তু
  শিশুর প্রোফাইল, ম্যাচিং ও প্রগ্রেস রিপোর্ট এখনো নেই (পরের ধাপ)
- **ইফতার ক্যালেন্ডার** — কোন তারিখ কে স্পনসর করেছে, রমজানের গ্রিড ভিউ
- **অনলাইন পেমেন্ট গেটওয়ে** ও **ওয়েবসাইটে লাইভ প্রগ্রেস বার**
  (`campaigns.is_public` ঘর এর জন্যই রাখা)
- দাতার একাধিক মোবাইল নম্বর

### শিশু-সুরক্ষা: একটিই দরজা

দাতার কাছে কী যাবে, তার সিদ্ধান্ত এক জায়গায় — `orphan-service.js` এর
`_safeChild()`। এটি **হোয়াইটলিস্ট**: যে ঘর এখানে স্পষ্টভাবে লেখা নেই, সেটি কখনো
বেরোয় না। পরে টেবিলে নতুন কলাম যোগ করলেও আপনাআপনি ফাঁস হবে না — এটাই
ব্ল্যাকলিস্টের চেয়ে নিরাপদ।

**দাতা দেখেন:** পরিচিতি কোড, নিয়ম অনুযায়ী নাম, বয়স, লিঙ্গ, অবস্থা (পিতৃহীন /
উভয়হীন …), শ্রেণি, বিভাগ, জেলা, ভর্তির তারিখ, মাসিক প্রয়োজন, স্বাস্থ্যের সাধারণ
তথ্য, আর সম্মতি থাকলে ছবি।

**দাতা দেখেন না:** পুরো নাম (নিয়ম না বললে), পিতা-মাতার নাম, অভিভাবকের নাম ও
মোবাইল, বাড়ির ঠিকানা, থানা, যাচাইয়ের কাগজ, প্রাতিষ্ঠানিক নোট, শিক্ষার্থী আইডি।

> জেলা পর্যন্ত দেখানো হয়, এর নিচে নয় — স্পনসর সাধারণত অঞ্চল জানতে চান, কিন্তু
> থানা বা গ্রাম জানালে শিশুকে খুঁজে বের করা সহজ হয়ে যায়।
> চাইলে `new OrphanService(pool, { showDistrictToDonor: false })` দিয়ে জেলাও বন্ধ করা যায়।

পরীক্ষায় এটি ৯টি আসল গোপন মান ডেটাবেসে ভরে, তারপর দাতা-দৃশ্যমান JSON ও প্রিন্ট
পেজের পুরো টেক্সটে সেগুলো **খুঁজে দেখা হয়** — একটিও পাওয়া যায় না।

### ছবির সম্মতি তিন স্তরে

`none` (ডিফল্ট) · `sponsor_only` · `public`

সম্মতি না থাকলে ছবির **পথটুকুও** ফেরত যায় না, যদিও ডেটাবেসে ছবি থাকে।
সম্মতি তুলে নিলে ছবি সাথে সাথেই সব জায়গা থেকে অদৃশ্য হয়। ওয়েবসাইটে দেখানোর
সম্মতি (`public`) শুধু মুহতামিম দিতে পারেন, আর কে সম্মতি দিয়েছেন ও কবে —
সেটা রেকর্ডে থাকে (`consent_by`, `consent_date`, `consent_note`)।
একই নিয়ম প্রগ্রেস রিপোর্টের ছবি ও শিশুর হাতে লেখা চিঠির ক্ষেত্রেও।

### নাম দেখানোর নিয়ম

`first_only` (ডিফল্ট) — শুধু প্রথম নাম · `full` — পুরো নাম ·
`code_only` — শুধু `ORF-0001`। `display_name` ঘরে কিছু লিখলে সেটাই চলে।

### যাচাই ছাড়া স্পনসরশিপ নেই

মৃত্যু সনদ বা চেয়ারম্যান সার্টিফিকেট আপলোড না করলে যাচাই করা যায় না, আর যাচাই
শুধু মুহতামিম করতে পারেন। যাচাই না হওয়া শিশু অসম্পৃক্ত পুলেও দেখানো হয় না —
অর্থাৎ দাতার সামনে যাওয়ার আগেই নথি নিশ্চিত হতে হয়।

### সরাসরি যোগাযোগ ও সাক্ষাৎ

`sponsorships.allow_direct_contact` ডিফল্টে `0`। খুলতে মুহতামিমের অনুমোদন ও
**লিখিত কারণ** লাগে (ডেটাবেস CHECK দিয়েও বাঁধা)। সব সাক্ষাৎ `orphan_visits` এ
লিপিবদ্ধ হয় — কে এসেছিলেন, কোন কর্মচারীর মধ্যস্থতায়, কী উদ্দেশ্যে।
দাতাকে পাঠানো রিপোর্টের নিচে লেখা থাকে যে শিশুর সাথে দেখা করতে হলে
প্রতিষ্ঠানের মাধ্যমে সময় নিতে হবে।

### স্পনসরশিপ: শেয়ারড ও ঘাটতি

কয়েকজন দাতা মিলে এক শিশুকে স্পনসর করতে পারেন; কভারেজ যোগ হয়ে
`v_orphan_summary` এ ঘাটতি ও শতকরা হিসাব হয়। প্রয়োজনের চেয়ে বেশি এলে
**আটকানো হয় না**, কিন্তু কত বেশি তা জানিয়ে দেওয়া হয় — সিদ্ধান্ত মানুষের।

**একটি হিসাবগত সূক্ষ্মতা:** মোট ঘাটতি = প্রতি শিশুর ঘাটতির যোগফল,
`মোট প্রয়োজন − মোট কভারেজ` নয়। এক শিশুতে অতিরিক্ত টাকা এলে তা অন্য শিশুর
ঘাটতি পূরণ করে না। তাই `overview()` আলাদা করে `over_covered_total` দেখায়,
আর সমীকরণটি হলো:

```
(মোট প্রয়োজন − মোট কভারেজ) + অতিরিক্ত কভারেজ = মোট ঘাটতি
```

### স্পনসরশিপ শেষ হলে শিশু আবার পুলে

`endSponsorship()` ফেরত দেয় নতুন ঘাটতি ও `back_to_pool` চিহ্ন, আর UI তখনই
সতর্ক করে — যাতে কেউ হঠাৎ অসহায় হয়ে না পড়ে। স্থগিত স্পনসরশিপও কভারেজে
গোনা হয় না, তাই শিশুটি সাথে সাথেই পুলে ফিরে আসে।

### প্রগ্রেস রিপোর্ট — স্পনসর ধরে রাখার চাবি

খসড়া অবস্থায় তৈরি হয়, মুহতামিম প্রকাশ করলে দাতা দেখতে পান এবং সব চলমান
স্পনসরশিপে `last_report_sent` বসে যায়। `reportsDue()` বলে দেয় কার রিপোর্ট
পাঠানোর সময় হয়েছে (মাসিক / ত্রৈমাসিক / ষাণ্মাসিক / বার্ষিক অনুযায়ী)।
রিপোর্টে থাকে উপস্থিতির হার, পরীক্ষার ফলাফল, হিফজের অগ্রগতি, স্বাস্থ্য,
শিক্ষকের মন্তব্য, ছবি আর শিশুর হাতে লেখা চিঠি — প্রিন্টযোগ্য A4 পাতায়।

### যা এখনো বাকি

- **দাতার নিজস্ব পোর্টাল** — `donorSponsorships()` ও নিরাপদ API তৈরি, কিন্তু
  দাতার লগইন ব্যবস্থা নেই। সেটি বসালে দাতা নিজেই রিপোর্ট দেখতে পাবেন
- **ফাইল আপলোড হ্যান্ডলার** — ছবি ও কাগজের টেবিল ও API প্রস্তুত, এখন পথ হাতে লিখতে হয়
- **SMS / ইমেইলে রিপোর্ট পাঠানো** — এখন প্রিন্ট করে বা হাতে পাঠাতে হয়
- এতিম নথিকে আপনার বিদ্যমান `students` টেবিলের সাথে জোড়া (`student_id` ঘর আছে,
  FK দেওয়া হয়নি কারণ সেটি অন্য মডিউলের টেবিল)
- **ইফতার/খাবার স্পনসর ক্যালেন্ডার** — রমজানের দৈনিক গ্রিড

## দুটি নকশাগত সিদ্ধান্ত যা মনে রাখা দরকার

**১. রিভার্স করা ভাউচার `posted` থেকেই যায়।** মূল এন্ট্রি খতিয়ানে রেখে বিপরীত
এন্ট্রি বসানো হয়, দুটি পরস্পরকে কাটে; মূল ভাউচারে শুধু `reversed_at` ও
`reversed_by_voucher_id` বসে। মূলটিকে খতিয়ান থেকে সরিয়ে দিলে রিভার্সালটি একা
থেকে জের উল্টো দিকে ঠেলে দিত (দ্বিগুণ প্রভাব) — পরীক্ষায় এটাই ধরা পড়েছিল।

**২. সব রিপোর্ট ভিউ-তে পোস্ট-ফিল্টার সাব-কোয়েরির ভেতরে INNER JOIN দিয়ে।**
`LEFT JOIN vouchers ... AND v.status='posted'` লিখলে শর্তটি লাইন বাদ দেয় না, শুধু
`v` কে NULL করে — ফলে ড্রাফট ও অনুমোদনের অপেক্ষায় থাকা ভাউচারও জেরে যোগ হয়ে যেত।
নতুন ভিউ বা রিপোর্ট লেখার সময় এই কাঠামোই অনুসরণ করুন।

## এখনো যা বাকি

- **সমসাময়িক পেন্ডিং ভাউচার:** একই ফান্ডে দুটি ভাউচার একসাথে `pending` হলে তৈরির
  সময় দুটোই পাস করতে পারে (পোস্টেড জেরের ভিত্তিতে যাচাই হয়)। পোস্টের সময় আবার
  যাচাই হয়, তাই ফান্ড ওভারড্রাফট হবে না — দ্বিতীয়টি পোস্টের সময় আটকাবে।
  চাইলে পেন্ডিং প্রতিশ্রুতিও গণনায় আনা যায়।
- **ওয়াকফের আয়:** কর্পাস সুরক্ষিত, কিন্তু ওয়াকফের আয়ের জন্য আলাদা ফান্ড
  (`WAQ-INC`) খুলে সেখান থেকে ব্যয় করতে হবে।
- **ব্যাংক রিকনসিলিয়েশন, বাজেট বনাম প্রকৃত, অবচয় স্বয়ংক্রিয়করণ** — পরের ধাপ।
- পিরিয়ড ক্লোজ ও বছর-সমাপনী (৩১৯৯-তে উদ্বৃত্ত স্থানান্তর) এখনো ম্যানুয়াল।
